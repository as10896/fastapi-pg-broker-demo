A message broker in one Postgres table

Producers INSERT rows. Consumers claim them with SELECT … FOR UPDATE SKIP LOCKED, so many consumers can pull from the same queue without ever receiving the same message. LISTEN/NOTIFY wakes idle consumers, leases recover messages from crashed consumers, and failed messages are retried with backoff until they land in the dead letter queue.

Message lifecycle

             claim                    ack
 pending ──────────────▶ processing ────────▶ done
    ▲                        │
    │                        │ nack or lease expired
    ├────────────────────────┤ retry (attempts < max)
    │                        │
    │ requeue                ▼ attempts ≥ max
    └───────────────────── dead

Claim uses FOR UPDATE SKIP LOCKED. Retries wait 2, 4, 8… seconds (at most 60).

Things to try

  1. Publish a burst of 200 messages and watch the worker drain it.
  2. On Workers, start more consumers, or run docker compose up -d --scale worker=3: throughput goes up, and no message is processed twice.
  3. Start a consumer with 5000 ms of work and kill it while it is busy, or run docker compose kill worker. Its message stays processing until the lease expires, then it is handed out again.
  4. Publish the Flaky and Poison presets, then open Dead letters.
  5. Run the locking experiment to see why SKIP LOCKED matters.
